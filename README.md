# card-game

덱빌딩 로그라이크 프로토타입. 지금은 서로 독립적인 프로토타입 **두 개**가 있다.

| 페이지 | 내용 |
| --- | --- |
| `index.html` | 전투 — 웨이브 총량만 공개하고 분배는 배치 확정 후 밝힌다 |
| `choice.html` | 2지선다 — 필드에 카드를 쌓으며 탈출하거나 죽는다 |

둘은 연결되어 있지 않다. `index.html`은 레인·웨이브 전투를 실험한 별개 프로토타입이고,
지금 게임의 본선은 `choice.html`이다. 전투는 현재 본선에 없다.

---

# 1. 전투 프로토타입 (`index.html`)

핵심은 **부분 정보**다. 웨이브가 시작되면 총 전력 숫자 하나만 공개되고, 그것이
각 레인에 어떻게 쪼개질지는 배치를 확정한 뒤에야 밝혀진다. 플레이어는 총량만
보고 추론하고 베팅한다.

## 실행

```bash
npm install
npm run dev        # 개발 서버 — /index.html 전투, /choice.html 2지선다
npm run typecheck
npm test           # 134개 테스트
npm run build
```

## 전투 규칙

**보드**: 3레인. 레인 하나는 두 칸이다.

| 칸 | 내용 |
| --- | --- |
| 위 | 이번 웨이브가 이 레인에 보낸 전력. 확정 전에는 `?` |
| 아래 | 배치한 플레이어 유닛 |

**웨이브 흐름**

1. **배치** — 총 전력만 공개된 상태에서 에너지를 써서 유닛을 깐다.
2. **확정** — 이 시점의 배치를 보고 분배가 정해지고 공개된다.
3. **교전** — 공개된 대로 부딪힌다. 웨이브는 한 번 부딪히고 소멸한다.

**전력 계산**

- 적 유닛은 **공격력 = 체력 = 배분된 전력**. 숫자 하나가 곧 위협의 크기다.
- 레인의 플레이어 전력 = 배치한 유닛의 **공격력 + 체력**.
- 위협이 레인 전력보다 크면 **넘치는 만큼만** 관통한다.
  화면의 "내 전력 7 vs 오는 전력 9"가 그대로 "2 관통"으로 읽힌다.
- 유닛이 받는 피해는 공격력만큼 깎인다. 공격력은 타격을 무디게 하고 체력은
  그 나머지를 버틴다.

**승리** 8웨이브를 버티면 승리. **패배** HP 0.

**손패** 누적, 매 웨이브 1장 드로우. **유닛** 죽을 때까지 필드에 남는다.

## 분배 규칙

`src/data/balance.ts`에 전부 모여 있다.

**패턴** — 균등형(1/1/1), 편중형(7/3/2), 2분할형(1/1/0), 몰빵형(10/1/1).
각 패턴은 `weightEarly`/`weightLate`를 가지며 웨이브 진행도로 선형 보간된다.
초반에는 균등형이 가장 흔하고, 후반으로 갈수록 몰빵형 비중이 올라간다.

**반응 강도** (`REACTIVITY`, 현재 0.55) — 0이면 분배 순서가 완전 무작위, 1이면
가장 얇은 레인이 항상 가장 큰 몫을 받는다. 중간값에서는 경향은 있되 확정적이지
않아서, 한 레인을 일부러 비워 유인하는 플레이가 성립하되 100% 읽히지는 않는다.

분배는 미리 뽑아두고 숨기는 것이 아니라 **확정 순간에 만들어진다**. 같은 시드라도
플레이어 배치가 다르면 분배가 달라진다.

## 밸런스

자동 플레이 400판 기준 **승률 61%, 승리 시 잔여 HP 3.4/12**.
총 전력 곡선은 `3 → 4 → 5 → 7 → 8 → 9 → 11 → 12`.

수치를 만질 때 알아야 할 것:

- **곡선이 플레이어 보드 전력을 추월하면 승률이 0으로 떨어진다.** 3레인에 유닛
  하나씩이면 현실적인 보드 전력 상한이 12~15다. 곡선을 여기 위로 올리면 후반
  웨이브를 구조적으로 못 막는다 (곡선 `4..17`로 400판 승률 0%).
- **에너지 2로는 3레인을 못 채운다.** 빈 레인은 위협을 통째로 맞으므로 승률이
  18%까지 떨어진다. 3이어야 "세 칸을 얇게 vs 두 칸을 두껍게"가 선택지가 된다.
- **적을 필드에 남기면 죽음의 나선이 된다.** 적 체력 = 전력인데 플레이어
  공격력은 0~5라 전력 7 이상은 잡히지 않는다. 잔존 적을 매 웨이브 증강시켰더니
  한 레인 위협이 22까지 올라가고 승률 0%가 나왔다. 그래서 웨이브는 한 번
  부딪히고 소멸한다.

## 구조

```
src/data/balance.ts    조정 가능한 밸런스 수치 (전부 여기)
src/data/cards.ts      플레이어 카드 정의
src/engine/rng.ts      시드 기반 결정론적 RNG
src/engine/wave.ts     총 전력 분배 — 패턴 선택 + 반응 강도
src/engine/combat.ts   전투 규칙 (DOM 의존 없음)
src/engine/types.ts    타입
src/ui/render.ts       DOM 렌더링 (상태를 읽기만 한다)
tests/                 Vitest
```

무작위는 전부 인자로 받은 `Rng`를 통해서만 발생하므로, 같은 시드와 같은 배치는
같은 전투를 재현한다.

## 기록

`state.records`에 웨이브별로 남는다 (`WaveRecord`): 총 전력, 뽑힌 패턴, 실제
분배, 레인별 플레이어 배치 전력, 총량 대비 여유(`margin`), 레인별 결과
(`held` / `traded` / `broken` / `leaked` / `clear`), 그 웨이브에 입은 피해.

# 2. 2지선다 프로토타입 (`choice.html`)

빨강/파랑 버튼을 누르면 덱이 즉시 바뀌고 다음 선택지가 나온다. 덱을 **실제로
쓰는 순간**이 선택지 안에 있어서, 쌓인 저주가 그때 물어뜯는다.

주된 재미는 버튼 딜레마이고, 전투는 그 선택의 결과를 청구하는 장치다.

슬레이 더 스파이어와의 차이: **보상이 희소하지 않다.** 전투 1회당 보상 1회가
아니라 제한 없이 계속 누를 수 있다. 한 번의 선택은 가볍지만 누적되면 덱이
완전히 달라진다.

## 루프

선택지 제시 → 한쪽 선택 → 덱에 즉시 반영 → 다음 선택지. 무한 반복.
끝나는 길은 둘, **탈출**(파편 3개)과 **사망**(체력 0)이다.

## 저주가 아픈 자리

저주에 페널티가 없으면 덱에 쌓여도 두려울 이유가 없고, 파편의 대가도 공짜가
된다. 저주가 무는 자리는 **필드**다 — 덱에 있는 동안은 아무 일도 하지 않지만,
뽑혀서 필드에 놓이는 순간 판정한다.

그래서 덱의 저주 비율이 그대로 "다음 뽑기의 위험도"다. 덱 패널에 `저주 8 /
전체 25`와 함께 **덱에 남아 아직 뽑힐 수 있는 저주**를 종류별로 못박아 둔다 —
이유를 모른 채 죽지 않도록.

한때는 덱을 뽑아 공개하고 저주 장수만큼 체력을 깎는 "덱소비형" 선택지가 이
역할을 했다. 필드가 생기면서 저주는 필드에서 물게 됐고, 공개 선택지는 전부
실제 뽑기(`drawField`)로 바뀌었다.

## 필드

뽑은 카드는 **쓰는 것이 아니라 필드에 펼쳐진 채로 남는다.** 소모라는 개념이 없다
— 잉카의 황금에서 뒤집힌 카드가 계속 앞에 쌓이는 것과 같다.

카드는 **덱 → 필드 한 방향으로만** 흐른다. 되돌아가는 길은 없고, 버린 더미도
재순환도 없다. 필드에서 벗어나는 길은 **선택지를 통한 제거뿐이다** —
발동한 저주도 그대로 남는다.

게임은 **필드 0장, 덱 20장**으로 시작한다. 필드는 오직 선택지를 통해서만
채워지고, 상한은 없다.

**시작 덱에는 저주가 종류별로 한 장씩 들어 있다** (파멸·부패·침식 각 1장).
한때는 저주가 한 장도 없었는데, 그러면 초반에 아무 버튼이나 눌러도 되는
구간이 길어진다. 첫 장부터 "한 장만 더 들어오면 터진다"가 걸려 있어야
선택이 처음부터 선택이 된다. 총 20장은 그대로고, 자리는 가장 많이 중복되던
중립 세 장에서 뺐다.

**그래서 필드는 스스로 줄지 않는다.** 뽑을수록 위험이 올라가고, 유일한
출구는 제거 선택지다 — 필드가 깨끗할 때는 시시하고, 저주가 여러 장 깔려 있으면
생명줄이 된다.

덱이 바닥나면 더 뽑을 수 없고 그 시점만 로그에 남긴다 (이후 처리는 설계 전).

## 저주 — 놓이는 순간 판정한다

저주는 전부 **필드에 놓이는 순간** 한 번 판정한다. 매 선택마다 필드를 훑는
지속 효과는 없다. 그래서 같은 저주가 반복 발동하지 않고, 발동 시점이 항상
플레이어가 뽑기를 누른 순간과 일치한다.

**세 저주는 공격 대상이 모두 다르다.**

| 저주 | 노리는 것 | 발동 조건 | 효과 |
| --- | --- | --- | --- |
| 파멸 | **목숨** | 필드에 `DOOM_THRESHOLD`(3)장 | 즉시 사망 |
| 부패 | **덱** | 필드에 `ROT_THRESHOLD`(2)장 이상일 때 하나 더 놓일 때 | 그 시점의 필드 부패 장수만큼 덱의 보상·중립이 부패로 바뀐다 |
| 침식 | **체력** | 없음 — 놓이면 즉시 | 체력 -`ERODE_DAMAGE`(2) |

- **발동해도 필드에서 사라지지 않는다.** 필드에서 벗어나는 길은 제거 선택지뿐이다.
- 부패는 **새로 놓일 때만** 1회 발동한다. 2장이 되는 순간 덱 2장, 거기서 3장째가
  놓이면 덱 3장 — 자기 자신을 늘려 계단식으로 나빠진다.
- 침식은 문턱도 중첩도 없다. 놓일 때마다 매번 같은 만큼 문다.

문턱이 높을수록 결과가 무겁다. 파멸은 2장 구간이 **최대 긴장**이고, 부패는
1장만 있어도 다음 한 장이 곧 발동이다.

### 화면

- 종류별로 **현재 장수와 문턱을 함께** 띄운다 — `파멸 2/3`, `부패 1/2`.
  침식은 문턱이 없어 장수만 센다.
- 문턱 직전인 종류는 배지가 맥동하고, 아래에 한 줄 경고가 붙는다.
- 부패가 깔려 있으면 **다음에 몇 장이 썩는지 미리** 보여준다 —
  "다음 부패가 놓이면 — 덱에서 2장이 부패로 바뀐다". 모르고 누르면 사고다.
- 발동하면 어떤 카드가 바뀌었는지 로그에 이름으로 남는다.

## 선택지 — 짝 테이블

`src/choice/pairs.ts`에 **빨강/파랑 한 쌍이 통째로** 들어 있다. 짝은 고정이고
자동 조합은 하지 않는다. 지금 11개다.

**왜 고정인가.** 낱개 선택지를 태그로 자동 조합하면 양쪽의 무게가 맞지 않는
짝이 나온다 — "저주 전부 제거" 맞은편에 "값싼 3장 버리기"가 놓이면 그건
딜레마가 아니라 무료 보상이다. 밸류 태그와 반대편 규칙으로 막아 위반을 0회까지
줄여 봤지만, 그 규칙은 "무게가 얼추 비슷한 것끼리 붙인다"까지만 할 수 있고
**이 둘을 붙이면 무엇을 묻는 질문이 되는가**는 표현하지 못한다. 짝을 고정하면
양쪽 무게를 의도적으로 설계할 수 있다.

폐기한 자동 조합 시스템은 `src/choice/retired/`에 남겨 두었다 (빌드에서 제외).

### 짝 하나의 구조

```ts
{
  id: 'shard-or-cleanse',
  rarity: 'ultra',
  intent: '탈출에 다가갈 것인가, 위협에서 벗어날 것인가',  // 화면에 안 나온다
  red:  { text: '…', effects: [...] },
  blue: { text: '…', effects: [...] },
}
```

`intent`는 게임에 노출되지 않는다. 없으면 "이 짝이 무엇을 묻는가"를 나중에
아무도 복원할 수 없어서 데이터에 박아 둔다.

### 11개 짝

| id | 희소도 | 묻는 것 |
| --- | --- | --- |
| `swell` | 보통 | 필드와 덱을 동시에 불릴 것인가, 최소한만 건드릴 것인가 |
| `seal` | 희귀 | 이후 5번의 선택을 제약한다. 어느 쪽을 봉인할지 |
| `shard-or-cleanse` | 매우 희귀 | 탈출에 다가갈 것인가, 위협에서 벗어날 것인가 |
| `purge-or-heal` | 매우 희귀 | 가까운 미래를 살 것인가, 지금을 살 것인가 |
| `quality-or-bulk` | 흔함 | 질이냐 양이냐 |
| `heal-for-taint` | 보통 | 지금 살기 위해 미래를 오염시킬 것인가 |
| `look-or-grab` | 보통 | 정보를 살 것인가, 물량을 택할 것인가 |
| `blood-for-deck` | 흔함 | 체력을 팔아 덱을 살 것인가 |
| `future-costs-now` | 보통 | 미래를 사는 값을 현재에서 치른다 |
| `field-bet` | 보통 | 필드 크기를 조건으로 삼는 베팅 |
| `taint-tempo` | 흔함 | 저주 유입 템포 — 분산이냐 집중이냐 |

`taint-tempo`의 빨강은 **종류별로 한 장씩**(파멸·부패·침식 각 1장), 파랑은
**무작위 2장**이다. 빨강은 확정적이고 파랑은 같은 종류가 겹쳐 나올 수 있다
(약 39% 확률).

**빨강은 `addSpecific`으로 넣으므로 파멸 덱 상한(3장)을 거치지 않는다.**
상한은 무작위 저주 생성 경로(`makeCurse`)에만 걸려 있다. "확정적"이 이 쪽의
성질이라 그렇게 뒀지만, 결과는 아래 "알려진 문제"에 적었다.

**반복 등장은 의도된 것이다.** 목적은 각 짝이 상황에 따라 다르게 읽히는지
검증하는 것이다. 같은 짝이 다시 나왔을 때 다른 쪽을 고르게 된다면 그 짝은
살아 있고, 항상 같은 쪽을 고른다면 죽은 짝이다.

희소도 가중치는 `PAIR_RARITY_WEIGHT`. 최근 `RECENT_PAIRS`(3)개는 다시 뽑지
않는다 — 11개뿐이라 이 값이 크면 순번 돌리기가 된다.

## 지속 효과

선택의 결과가 즉시 끝나지 않고 이후 N회의 선택에 걸쳐 유지되는 것. 지금은
`seal` 짝 하나가 쓴다.

- 남은 횟수는 **화면에 항상 떠 있다.** 제약을 잊고 누르면 딜레마가 아니라
  사고가 된다. 그래서 패널에 남은 횟수를 띄우고, 봉인된 **버튼 위에도**
  "누르면 체력 -5"를 붙인다 — 패널만으로는 누르는 순간에 안 보인다.
- 여러 개가 동시에 걸릴 수 있다.
- 무슨 선택을 하든 남은 횟수는 1씩 준다. 봉인된 색을 피해 다니면 피해 없이
  흘려보낼 수 있고, 그래서 "5회 동안 한쪽을 못 쓴다"가 제약이 된다.
- 같은 제약을 다시 걸면 쌓이지 않고 남은 횟수가 다시 채워진다. 두 줄로 쌓이면
  어느 쪽이 언제 풀리는지 화면에서 읽을 수 없다.

## 탈출과 사망

파편 **3개**를 모으면 탈출, 체력이 0이 되면 사망. 마지막 파편을 캐다 죽으면
탈출이 아니라 사망이다 (죽음을 먼저 판정한다).

**파편을 주는 것은 `shard-or-cleanse`의 빨강 하나뿐이다.** 그래서
`ESCAPE_TARGET`과 `PAIR_RARITY_WEIGHT.ultra`가 함께 한 판의 길이를 정한다.
ultra 12에서는 그 짝이 4%만 떠서 파편 3개에 중앙 70수가 걸렸고, 25로 올리니
40수가 됐다.

그 짝의 파랑은 "덱의 모든 저주를 제거"다. 탈출 진척과 위협 제거가 같은 화면에서
맞선다 — 파편을 집으면 저주 1장이 덱에 더 들어오므로, 급할수록 덱이 나빠진다.

## 밸런스

`src/choice/balance.ts`에 모여 있다. 시뮬레이션으로 잡은 것들:

- **짝이 11개뿐이라 밸런스는 아직 조절 대상이 아니다.** 선택지가 적으면 잘 두는
  쪽이 거의 항상 이긴다. 자동 플레이 400판:

  | 정책 | 탈출 | 중앙 |
  | --- | --- | --- |
  | 아무렇게나 반반 | 3% | 23수 |
  | 상황을 보고 고른다 | 26% | 68수 |

  지금 수치가 보증하는 것은 "아무렇게나 누르면 죽는다"까지다.
- **시작 덱에 저주를 넣으면 겹침이 앞당겨진다.** 800판씩 비교:

  | | 첫 겹침 중앙 | 겹침을 본 판 | 총 발동 | 10수 이내 사망 |
  | --- | --- | --- | --- | --- |
  | 이전 (저주 0장) | 25수 / 40수 | 21% / 28% | 342 / 376회 | 7% / 0% |
  | 지금 (종류별 1장씩) | **17수 / 32수** | **31% / 37%** | **533 / 516회** | 10% / 1% |

  (왼쪽이 아무렇게나, 오른쪽이 상황 판단 정책)

  첫 겹침이 8수 앞당겨지고 발동 횟수가 40~55% 늘었다. **조기 사망은 과하지
  않다** — 5수 이내 사망은 800판 중 2~4판(0~1%)이다.

  다만 1~5수 안에 실제로 겹치는 판은 800판 중 9~12판(약 1%)뿐이고, 판의
  절반 이상(63~69%)은 끝까지 한 번도 겹치지 않는다. 덱에 심어 둔 긴장이
  실제 사건이 되기까지는 여전히 시간이 걸린다.
- **짝을 2개 더하면 한 판이 길어진다.** 9개일 때 상황 판단 플레이는 중앙 40수에
  끝났는데 11개가 되자 81수로 늘었다. 파편을 주는 짝이 하나뿐이라, 흔함·보통
  짝이 늘면 그만큼 파편 짝의 몫이 줄어든다(7% → 5%). `taint-tempo`가 저주를
  꾸준히 밀어 넣는 것도 겹친다.
- **체력 20 / ultra 가중치 25.** 이 둘이 한 판의 길이를 정한다. ultra를 12로
  두면 파편 짝이 4%만 떠서 중앙 70수까지 늘어진다.
- **덱 크기**: 무작위 플레이 100회에 40장 안팎. 항상 덱이 커지는 쪽만 골라도
  250회에 120장을 넘지 않는다.
- **덱이 불어나던 문제**: 처음에는 비용이 대부분 "저주 추가"라 양쪽 다 선택당
  +1장이었고, 탐욕만 고르면 400회에 869장까지 갔다. 비용을 **잃는 것**으로
  바꾸고 나서 탐욕 플레이도 현실적인 구간(20~40회)에서 18~29장에 머문다.
- **파편과 저주는 "값싼 카드 정리"에서 제외된다.** 둘 다 값어치가 낮아 그냥
  두면 짐을 덜어낼 때마다 먼저 잘려 나간다. 파편은 탈출 카운트가 어긋나고,
  저주는 공짜로 청소돼 오염도가 5%를 못 넘었다 — 저주 페널티 자체가 성립하지
  않아 무지성 탈출률이 99%였다. 저주는 정리형 선택지로만 지운다.
- **종류 없는 저주**: 카드 생성 함수가 `effects.ts`와 `field.ts`에 하나씩 있었고
  전자가 `curseType`을 빠뜨렸다. 그래서 변환(`transform`)으로 만들어진 저주는
  껍데기였다 — 필드에 깔려도 겹치지 않고, 부패라면 갉지도 않고, 파멸이라도
  죽이지 않았다. 오염도 숫자만 올랐다. 화면에서 필드에 파멸이 놓여 있는데 집계
  배지가 `파멸 0`인 것을 보고 찾았다. 변환도 이제 `makeCurse`를 거쳐 파멸 덱
  상한을 지킨다("중립이 전부 저주가 된다" 한 방으로 파멸이 쏟아지던 구멍).

## 알려진 문제

**두 짝은 답이 잘 바뀌지 않는다.** 하나의 평가 함수로 400판을 돌려 짝별
빨강 선택률을 보면:

| 짝 | 빨강 | |
| --- | --- | --- |
| `swell` | 57% | 상황따라 갈림 |
| `seal` | 91% | 거의 안 바뀜 |
| `shard-or-cleanse` | 34% | 상황따라 갈림 |
| `purge-or-heal` | 40% | 상황따라 갈림 |
| `quality-or-bulk` | **2%** | 거의 안 바뀜 |
| `heal-for-taint` | 9% | 거의 안 바뀜 |
| `look-or-grab` | 77% | |
| `blood-for-deck` | **1%** | 거의 안 바뀜 |
| `future-costs-now` | 78% | |
| `field-bet` | 9% | 거의 안 바뀜 |
| `taint-tempo` | **0%** | 거의 안 바뀜 |

`quality-or-bulk`(보상 1 vs 중립 3)와 `blood-for-deck`(보상 3+피해 4 vs 중립 2)은
**양쪽 다 덱만 건드리고 필드·저주·체력 상태와 거의 무관하다.** 상황이 바뀌어도
답을 뒤집을 근거가 게임 안에 없다.

`taint-tempo`는 의도가 "덱·필드의 저주 구성에 따라 유리한 쪽이 달라진다"인데
지금 수치로는 그렇게 되지 않는다. 아래 "알려진 문제" 참조.

다만 이 수치는 사람이 아니라 **하나의 평가 함수**가 고른 결과다. 짝이 죽었는지는
사람이 반복해서 눌러 봐야 확정할 수 있고, 이번 단계의 로그는 그것을 재기 위한
것이다.

**덱이 바닥난 뒤가 비어 있다.** 20장을 다 뽑으면 뽑기 선택지가 아무 일도 하지
않는다 — 로그에 "덱이 바닥났다"만 한 번 남고 규칙은 없다.

**`taint-tempo`의 빨강이 지배당한다.** 의도는 "분산이냐 집중이냐"이고
상황에 따라 답이 갈려야 하는데, 그렇게 되지 않는다. 빨강만/파랑만 고르도록
고정하고 600판씩 돌린 결과:

| taint-tempo | 탈출 | 중앙 | 파멸사 | 종료 시 덱 저주 | 파멸 최대 보유 |
| --- | --- | --- | --- | --- | --- |
| 빨강 (종류별 1장씩) | 20% | 25수 | 42판 | 11.1장 | **11장** |
| 파랑 (무작위 2장) | 18% | 23수 | 23판 | 7.6장 | 3장 |

빨강은 **3장**을 주고 파랑은 **2장**을 준다. 게다가 빨강은 매번 파멸을
확정으로 하나 끼워 넣는다 — 겹치면 즉사하는 종류다. 그래서 상황과 무관하게
빨강이 더 나쁘고, "분산이라 겹침이 느리다"도 성립하지 않는다 (저주 발동
총합이 빨강 265회 / 파랑 194회로 오히려 빨강이 많다. 장수가 50% 많아서다).

그리고 **파멸 덱 상한 3장이 무력해진다.** 빨강이 상한을 거치지 않으므로
파멸이 최대 11장까지 쌓였다. "파멸은 1장만 보여도 긴장"이라는 규칙이
이 짝 하나로 깨진다.

수치는 스펙대로 넣었으므로 그대로 두었다. 의도대로 만들려면 셋 중 하나가
필요해 보인다 — 빨강에서 파멸을 빼거나, 빨강도 상한을 거치게 하거나,
파랑을 3장으로 올려 장수를 맞추거나.

**세 저주의 위협도가 맞는지는 아직 확인 전이다.** 규칙은 스펙대로 넣었고
(파멸 3 / 부패 2 / 침식 2), 실제로 셋이 비슷한 무게로 느껴지는지는 직접
플레이해서 판단한다. 그때 볼 값은 `state`에 전부 쌓인다 — 종류별 발동 횟수,
종류별 필드 최고 도달 장수, 침식 누적 피해, 부패로 썩은 카드 수, 사망 원인.

조정할 곳은 세 군데다. 발동 문턱(`DOOM_THRESHOLD` / `ROT_THRESHOLD`)과
피해량(`ERODE_DAMAGE`), 그리고 저주가 만들어지는 비율인 `CURSE_RULES`의
`weight`(지금 파멸 1 : 부패 2 : 침식 3). 파멸이 잘 안 보인다면 문턱보다
가중치 쪽이 먼저다 — 파멸은 저주 6장 중 1장꼴로만 만들어지는데 그것을 셋이나
동시에 필드에 올려야 발동한다.

**푸시 유어 럭이 테이블 밖에 있다.** 규칙은 살아 있지만 11개 짝 중 어느 것도
쓰지 않아 지금 빌드에서는 닿을 수 없다.


## 구조

```
src/choice/balance.ts   조정 가능한 수치 + 카드 풀 + 시작 덱 + 희소도 가중치
src/choice/pairs.ts     짝 테이블 11개 (데이터만)
src/choice/effects.ts   덱·필드 조작 효과 + 지속 효과
src/choice/retired/     폐기한 자동 짝짓기 시스템 (빌드 제외, 참고용)
src/choice/field.ts     필드 — 뽑기, 놓일 때의 저주 판정, 제거
src/choice/engine.ts    선택 루프, 이벤트 추첨, 덱 요약
src/choice/render.ts    DOM 렌더링
src/choice/types.ts     타입
```

`state.records`에 선택마다 남는다: 이벤트 id, 고른 쪽, 문구, 변화 요약,
선택 후 덱 크기·저주 수·체력.

필드 시스템은 따로 남긴다: `triggers`(저주 종류별 발동 횟수), `causeOfDeath`
(어떤 저주가 겹쳐 죽었는지), `fieldSizes`(매 선택 후 필드 크기 — 평균용),
`riskyDraws`(저주 1장이 깔린 상태에서 더 뽑은 횟수와 그중 겹친 횟수),
`deckEmptiedAt`(덱이 바닥난 시점). 사망·탈출 로그에는 그 시점의 필드 크기와
덱 잔량이 함께 남는다.

## 로그 — 이번 단계의 핵심

짝이 11개뿐이므로 목적은 밸런스가 아니라 **각 짝이 살아 있는지 재는 것**이다.
`GameState`에 남는 것:

| 값 | 내용 |
| --- | --- |
| `pairStats[id]` | 짝별 `seen` / `red` / `blue`. **빨강/파랑 비율이 가장 중요하다** |
| `rarityStats` | 희소도별 등장 횟수 |
| `records[]` | 선택마다 `pairId`, 고른 쪽, 그리고 **그 시점의** `deckSize` / `fieldSize` / `curseCount` / `hp` |
| `step` | 사망 또는 탈출까지의 선택 횟수 |
| `firstPairAt` | 저주가 **처음 발동한** 선택 번호 |
| `peakField` | 저주 종류별로 필드에 동시에 몇 장까지 쌓였는지 |
| `erodeDamage` | 침식이 깎은 체력 누적 |
| `rotConverted` | 부패가 덱에서 썩힌 카드 총 장수 |
| `causeOfDeath` | 무엇에 죽었는지 |
| `deckEmptiedAt` | 덱이 바닥난 선택 번호 |

상태 스냅숏은 선택 **직전**에 찍는다. "같은 짝이 상황에 따라 다르게 읽히는가"를
보려면 결과가 아니라 그때 무엇이 보였는지가 필요하다.

한쪽으로 90% 이상 쏠린 짝은 딜레마가 아니다.

## 아직 정하지 않은 것

- **`swell` 빨강의 "무작위 카드 2장"이 무엇인가.** 지금은 보상/중립/저주를
  가리지 않고 뽑는 것으로 구현했다(파편 제외). 저주가 섞이므로 "불린다"가
  도박이 된다 — 다른 의도였다면 `addAny`를 고치면 된다.
- **바닥 타일 덱(맵 구성)** 도입 여부.
- **전투와 선택의 연결** — 지금 둘은 완전히 분리된 페이지다.
- **웨이브가 곡선에서 생성되므로** "몬스터 덱에 추가" 형태의 선택지는 지금
  구조에 붙지 않는다. 선택지로 곡선이나 패턴 확률, 반응 강도를 건드리는 쪽이
  맞을 수 있다.
- **저주의 실제 효과** — 전투가 정해지면 오염도에 의미를 붙일 수 있다.
